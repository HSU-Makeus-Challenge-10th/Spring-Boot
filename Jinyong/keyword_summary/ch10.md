- 클라우드 컴퓨팅이란?

  클라우드 컴퓨팅은 서버, 저장소, 네트워크, 데이터베이스 같은 IT 자원을 직접 구매해서 운영하지 않고, AWS나 GCP 같은 클라우드 서비스 제공업체로부터 빌려 사용하는 방식이다.(임대 개념!! 서버 빌려씀)

  예전에는 기업이 직접 서버실을 만들고 장비를 구매해야 했지만, 클라우드 컴퓨팅을 사용하면 필요한 만큼만 서버를 만들고, 필요 없어지면 반납도 가능하다. 그래서 초기 비용을 줄일 수 있고, 서비스 규모가 커지면 서버 성능을 높이거나 서버 개수를 늘리는 식으로 유연하게 대응할 수 있다.

  클라우드 컴퓨팅의 장점은 다음과 같다.

    1. 서버를 직접 구매하지 않아도 되어 초기 비용이 줄어든다.
    2. 사용량에 따라 자원을 늘리거나 줄일 수 있어 확장성이 좋다.
    3. 여러 지역에 서버를 둘 수 있어 장애 대응과 속도 개선에 유리하다.
    4. 배포와 운영을 자동화하기 좋다.

  단점도 있다. 사용량을 잘못 관리하면 예상보다 비용이 많이 나올 수 있고(과금주의!), 클라우드 구조를 잘 모르면 보안 설정을 잘못할 위험도 있다. 따라서 클라우드는 편리하지만, 비용 관리와 보안 설정을 함께 신경 써야 한다.

- AWS? GCP?

  AWS는 Amazon Web Services의 약자로, 아마존에서 제공하는 클라우드 컴퓨팅 서비스이다. EC2, S3, RDS, VPC, Lambda 등 다양한 서비스를 제공하며, 서버 생성, 데이터 저장, 데이터베이스 운영, 네트워크 설정, 배포 자동화 등에 사용할 수 있다.

  GCP는 Google Cloud Platform의 약자로, 구글에서 제공하는 클라우드 서비스이다. Compute Engine, Cloud Storage, Cloud SQL, BigQuery 등 다양한 서비스를 제공한다. 특히 데이터 분석, 머신러닝, AI, 빅데이터 처리 쪽에서 강점이 있다.

  AWS와 GCP는 모두 클라우드 서비스 제공업체라는 공통점이 있다. 둘 다 서버를 빌려 쓰고, 데이터베이스를 운영하고, 저장소를 만들고, 배포 환경을 구성할 수 있다.

  차이점은 서비스 이름, 콘솔 구조, 요금 체계, 강점 분야가 조금씩 다르다는 점이다.

  AWS는 레퍼런스가 많고 실제 기업에서 많이 사용되기 때문에 초보자가 자료를 찾기 쉽다.. 반면 GCP는 구글 생태계와 연결성이 좋고, 데이터 분석이나 AI 관련 서비스에서 강점이 있다.

- 환경변수 처리 방법과 왜 환경변수로 민감 정보를 가려야 하는가?

  환경변수는 애플리케이션 **실행에 필요한 설정값을 코드와 분리해서 관리하는 방법**이다. 예를 들어 DB 주소, DB 아이디, DB 비밀번호, JWT Secret Key, OAuth Client ID, SSH Key 같은 값들은 코드에 직접 적으면 위험하다.(Github에 push하면 사고…) 이런 값들을 환경변수로 빼두면 코드에는 `${DB_PASSWORD}` 같은 형태만 남기고, 실제 값은 서버나 GitHub Secrets에서 관리할 수 있다.

  환경변수 처리가 필요한 가장 큰 이유는 **보안** 때문이다. 만약 `application.yml`에 DB 비밀번호나 JWT Secret Key를 직접 적고 GitHub에 올리면, 다른 사람이 해당 정보를 보고 DB에 접근하거나 토큰을 위조할 수 있다. 특히 Public Repository라면 민감 정보가 그대로 노출될 위험이 크다.(항상 조심)

  환경변수를 처리하는 방법은 여러 가지가 있다. 로컬 개발 환경에서는 `.env` 파일을 사용할 수 있고, 서버에서는 EC2 내부에 `.env` 파일을 만들어 사용할 수 있다. GitHub Actions에서는 GitHub Secrets에 민감 정보를 저장한 뒤 워크플로우에서 `${{ secrets.이름 }}` 형태로 불러올 수 있다.

  Spring Boot에서는 기본적으로 `.env` 파일을 자동으로 읽지 않기 때문에, `application.yml`에 다음과 같은 설정을 추가해야 한다.

    ```yaml
    spring:
      config:
        import: optional:file:.env[.properties]
    ```

  이렇게 하면 `.env`에 저장한 값을 Spring 설정에서 불러와 사용할 수 있다.

- yml 환경 분리 방법

  `yml` 환경 분리는 개발 환경, 테스트 환경, 운영 환경에서 **서로 다른 설정을 사용하기 위해 필요**하다.

  예를 들어 로컬 개발에서는 내 컴퓨터의 MySQL을 사용하지만, 운영 서버에서는 EC2나 RDS에 있는 DB를 사용할 수 있다. 이때 하나의 `application.yml`에 모든 설정을 넣으면 관리가 복잡해지므로 환경별로 설정 파일을 나누는 것이 좋다.

  대표적인 방식은 다음과 같다.

    ```
    application.yml
    application-local.yml
    application-dev.yml
    application-prod.yml
    ```

  `application.yml`에는 공통 설정과 현재 사용할 profile을 적는다.

    ```yaml
    spring:
      profiles:
        active: local
    ```

  그리고 `application-local.yml`에는 로컬 개발용 DB 설정을 넣고, `application-prod.yml`에는 운영 서버용 DB 설정을 넣는다.

  예시는 다음과 같다.

    ```yaml
    # application-local.yml
    spring:
      datasource:
        url: jdbc:mysql://localhost:3306/mydb
        username: root
        password: ${DB_PASSWORD}
    ```

    ```bash
    # application-prod.yml
    spring:
      datasource:
        url: ${DB_URL}
        username: ${DB_USERNAME}
        password: ${DB_PASSWORD}
    ```

  이렇게 분리하면 로컬에서는 `local` 프로필을 사용하고, 서버에서는 `prod` 프로필을 사용하면 된다. 실행할 때는 다음처럼 프로필을 지정할 수 있다.

    ```
    java-jar app.jar--spring.profiles.active=prod
    ```

- Docker와 .jar vs Docker 이미지

  Spring Boot 프로젝트를 배포하는 방법은 크게 `.jar` 파일을 직접 실행하는 방식과 Docker 이미지를 만들어 실행하는 방식으로 나눌 수 있다.

  `.jar` 방식은 Gradle로 프로젝트를 빌드한 뒤 생성된 `.jar` 파일을 서버에 올리고, 서버에서 직접 실행하는 방식이다.

    ```bash
    java-jar app.jar
    ```

  이 방식은 구조가 단순하고 처음 배포를 배우기에 좋다. EC2에 Java만 설치되어 있으면 실행할 수 있고, GitHub Actions로 `.jar` 파일을 서버에 전송한 뒤 실행하면 된다. 하지만 서버에 Java 버전, 환경변수, DB 접속 설정 등을 직접 맞춰야 하기 때문에 서버 환경에 영향을 많이 받는다.

  **Docker 방식**은 애플리케이션과 실행 환경을 하나로 묶어 Docker 이미지로 만든 뒤 실행하는 방식이다.

  **Docker 이미지**는 애플리케이션 실행에 필요한 Java 버전, 설정, 실행 명령어 등을 포함할 수 있다. 서버에서는 Docker만 설치되어 있으면 같은 이미지를 거의 동일한 환경에서 실행할 수 있다.

  즉, `.jar`는 실행 파일이고, Docker 이미지는 실행 파일과 실행 환경을 함께 포장한 배포 단위라고 볼 수 있다.

  `.jar` 방식의 장점은 간단하고 빠르게 배포할 수 있다는 점이다. 단점은 서버 환경이 달라지면 문제가 생길 수 있다는 점이다. Docker 이미지 방식의 장점은 어느 서버에서든 비슷한 환경으로 실행할 수 있고, 배포와 확장에 유리하다는 점이다. 단점은 Dockerfile, 이미지 빌드, 컨테이너 실행 같은 개념을 추가로 알아야 한다는 점이다.
